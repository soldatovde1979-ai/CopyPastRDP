## 2026-10-07 17:05 — [feat] Пакетная отправка очереди одним ZIP; таймаут ACK у ручной отправки

**Файлы:** `FileTransfer.ps1`, `setcp.ini`, `README.md`

- **ЧТО:** Пакетный режим синхронизации (`SyncBatchFiles=50`): когда в очереди SyncDir >= 50 НОВЫХ элементов (файлов + папок), они упаковываются в один архив `.syncbatch.synczip` (`New-SyncBatchZip`: файлы с относительными путями + манифест `_syncdirs.txt` со списком папок) и передаются одним файлом. Приёмник (`Expand-SyncBatch`) распаковывает в SyncDir, помечает содержимое RECEIVED, создаёт папки по манифесту, удаляет архив. При недоступности приёмника — backoff с фиксированным ключом: одна попытка в окно.
- **ПОЧЕМУ:** Перенос дерева из тысяч файлов/папок (выгрузка 1С «Diadok») шёл часами: каждая папка/файл — отдельный пакет с ожиданием ACK, при молчащем приёмнике — 60 сек на попытку. Буфер обмена при этом постоянно занят пакетами.
- **ЧТО:** Таймаут ACK у ручной отправки: `Send-FileInChunks` (не sync-режим) и ожидание PackAuto ограничены `SyncAckTimeoutSec` (60 сек). По таймауту — FATAL в журнале, файл НЕ удаляется из OUT.
- **ПОЧЕМУ:** Раньше потерянный ACK (пакет побит пользовательской работой с буфером) заставлял отправку висеть вечно — «большие файлы не копируются».
- **ЧТО:** `.synczip`-архивы исключены из обычной маршрутизации (как `.del` — строго в корень SyncDir).
- **ВАЖНО:** приёмнику нужна версия с `Expand-SyncBatch`: обновление доезжает через SyncDir автоматически при работающем удалённом слушателе.

## 2026-10-07 13:55 — [feat] Параметр -DebugLevel: два уровня подробности журнала

**Файлы:** `FileTransfer.ps1`, `setcp.ini`, `README.md`

- **ЧТО:** Параметр `-DebugLevel` (аргумент или ключ `Debug` в `setcp.ini`, по умолчанию 0). При `Debug=0` `Write-Log` не пишет подробные строки (Gray/DarkGray/Cyan — прогресс чанков, heartbeat `Watch alive`, trace, диагностика backoff) ни в журнал, ни в консоль — остаются ошибки (Red), предупреждения (Yellow) и конечные статусы операций копирования (Green: `OK: Sent N files`, `SUCCESS: ... fully transferred`, а также маркеры `===== START/END =====`). При `Debug=1` — полный лог как раньше.
- **ПОЧЕМУ:** По умолчанию пользователю нужен итог («файл передан/не передан»), а поток прогресса и heartbeat мешает; полный лог нужен только при диагностике.
- **ПОЧЕМУ:** Имя параметра — `DebugLevel`, а не `Debug`: скрипт с атрибутами `[Parameter()]` — advanced, имя `-Debug` занято встроенным общим параметром PowerShell; при объявлении `[int]$Debug` скрипт падал при старте («A parameter with the name 'Debug' was defined multiple times»), из-за чего слушатель после развёртывания 14:02 молча не работал до исправления.
- **Дополнительно:** README — раздел «Подробность журнала (-DebugLevel)»; `WatchHeartbeatSec`/`WatchTrace` в setcp.ini помечены как видимые только при Debug=1.

## 2026-10-07 12:40 — [feat+fix] Синхронизация пустых папок; backoff ретраев и восстановление буфера; маршруты на лету

**Файлы:** `FileTransfer.ps1`, `setcp.ini`

- **ЧТО:** 1) Синхронизация папок: пустые папки в SyncDir передаются новым пакетом `FILE_DISK_DIR` (функция `Send-SyncDirectory`, приём в `Watch-Clipboard` создаёт папку по `RelPath`); при снапшоте change.log папки помечаются `SNAPSHOT`; ключ папки стабилен (`dir/<rel>|0|0` — `Get-DirKey`/`Add-DirChangeEntry`), не зависит от mtime папки. Раньше переносились только файлы (папки возникали по RelPath файлов).
- **ПОЧЕМУ:** Пустые папки не переносятся никогда — их некому «нести»; пользователь кладёт в disk готовую структуру папок.
- **ЧТО:** 2) Backoff ретраев: после неудачной отправки (таймаут ACK — слушатель другого контура выключен) повтор откладывается на растущий интервал `SyncRetryDelaySec`×2^n, максимум `SyncRetryMaxDelaySec` (`Test-SyncRetryReady`/`Register-SyncFailure`/`Clear-SyncFailure`); счётчик сбрасывается при изменении файла. Применяется к файлам, папкам и маркеру `.del`.
- **ПОЧЕМУ:** Раньше ретрай шёл каждым сканом: в журнале видны часы попыток «чанк → таймаут 60 сек → ретрай» — буфер обмена постоянно забивался JSON-пакетами.
- **ЧТО:** 3) Восстановление буфера: перед отправкой пакета синхронизации/команды текст буфера сохраняется (`Save-ClipText`) и возвращается после попытки (`Restore-ClipText`) — в `Send-SyncFile`, `Send-SyncDirectory`, `Invoke-ClearDisk`.
- **ПОЧЕМУ:** Пользователь после каждой отправки находил в буфере «абракадабру» вместо своего текста.
- **ЧТО:** 4) Маршруты `[Routes]` перечитываются на лету: `Update-Routes` вызывается при каждом приёме пакета (`Unpack-Files`), правки INI подхватываются без перезапуска слушателя. Чтение INI вынесено в `Read-TextFile`: при сохранении файла в ANSI/cp1251 (Блокнот) русские маски не ломаются (fallback на системную кодировку при replacement-символах).
- **ПОЧЕМУ:** Маршруты читались один раз при старте — правка масок («Отчет по кач*») требовала перезапуска; сохранение INI не в UTF-8 ломало кириллицу в масках.
- **ЧТО:** 5) `Stop-OldListeners`/`Restart-WatchIfRunning`: старый слушатель ищется по командной строке независимо от имени процесса (powershell.exe/pwsh.exe) и порядка аргументов — по подстроке `FileTransfer.ps1` + слову `Watch`.
- **ПОЧЕМУ:** При запуске нового слушателя старый мог не быть убит (фильтр только по `powershell.exe` и точной подстроке) — двойной слушатель конкурирует за буфер.

## 2026-09-04 23:10 — [feat] Очистка папки disk маркер-файлом .del (команда MarkDelete)

**Файлы:** `FileTransfer.ps1`, `README.md`, `SPEC.md`

- **ЧТО:** Добавлена команда `MarkDelete` и обработка маркер-файла `.del` в `Scan-SyncDir`: пустой файл `.del` в корне `SyncDir` — триггер полной очистки папки на обоих контурах. Слушатель отправляет маркер на другой контур обычным чанковым механизмом (`RelPath` = `.del`), помечает его `SENT` и после подтверждения очищает локальную папку (`Clear-SyncDirLocal`); приёмник сохраняет маркер строго в корень `SyncDir` (маршрутизация `[Routes]` к маркеру не применяется) и при следующем скане очищает свою папку. Пока маркер не отправлен (слушатель другого контура выключен), очистка откладывается и повторяется при каждом сканировании. В журнале — префикс `DEL-MARKER:`.
- **ПОЧЕМУ:** Нужен способ очистки папок `disk` без командной строки: маркер можно положить вручную, а синхронизация сама доставит его на другой контур. Раньше была только команда `ClearDisk`, требующая запуска на одном из ПК; механизм маркер-файла ранее не реализовывался.
- **ПОЧЕМУ:** Восстановлен привычный порядок работы «сначала Send на источнике, затем RECEIVE FILE на приёмнике»: фоновый слушатель мгновенно принимает пакет в `InDir`, поэтому ручной приём должен забирать файлы оттуда, а не только из буфера.
