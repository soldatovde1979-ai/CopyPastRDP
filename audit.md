## 2. Плюсы решения

- **Единая чанковая отправка** `Send-FileInChunks` (FileTransfer.ps1:258) — одна реализация для ручной отправки и синхронизации, протокол не расползается.
- **Уровень подробности журнала** (`Debug=0/1`, Write-Log:235) — по умолчанию читаемый минимум, при диагностике полный лог. Ротация с дешёвой проверкой размера (:243).
- **Статус-обмен контуров** (status-*.json, :1514–1528) — дашборд видит оба контура без сетевых вызовов, только через синхронизацию папки.
- **LogTracker** — статистика, фильтры, поиск с номерами строк, `-Stats` без задвоения MB (LogTracker.ps1:186–194, с честным комментарием почему).
- **Стартовые строки ОТПРАВКА/ПРИЁМ** с размером и числом чанков (:291, :705) — передача видна с момента старта, а не только в итоге.

## 3. Минусы и слабые места решения

1. **Размытая семантика цвета — корень жалоб «всё зелёное, но столько ошибок».** В журнале зелёным (`Green`) пишутся и подтверждения, и служебные события: `OK: Sent N files to clipboard!` (:474) пишется **до** подтверждения приёмника; `SUCCESS: Sync file 'status-...' completely assembled!` (:742) каждые 30 сек засорял лог зелёным «успехом» сборки служебного файла (в живом логе 14:31–14:34 — каждые 30 сек; в текущем коде для `status-` уже подавлено). В дашборде зелёный = «отправка», синий = «приём» (dashboard.html:21, классификация FileTransfer.ps1:2132–2134) — т.е. цветом рутинного трафика стал статусный зелёный, и глаз перестаёт отличать «штатно» от «готово».
2. **Одна передача — несколько строк в разных местах.** Отправка 12-чанкового `materials2.zip` (живой лог 16:57–16:58) пишется строками ОТПРАВКА → ОТПРАВЛЕНО → SUCCESS fully transferred → END, между ними вклиниваются события других контуров/режимов. На веб-дашборде фильтр истории (:1986) не содержит `ОТПРАВКА|ПРИЁМ`, поэтому стартовая строка не показывается вовсе — передача видна «серединой», без начала. Это и есть жалоба «в лог передаётся целый чанк кусками, хочешь цельный кусок от начала до конца».
3. **`meta refresh=3` перезагружает страницу целиком** (dashboard.html:1): мигание, потеря прокрутки, и главное — **обрыв загрузки в drop-зоне**: `FileReader` + `XMLHttpRequest` не успевают за 3 сек, перезагрузка убивает запрос молча. Это причина свежего баг-репорта «после переноса в область в вебе ничего не происходит».
4. **Web-эндпоинты видят только `powershell.exe`** (:2072, :2089, :2138): слушатель, запущенный под `pwsh.exe` (PowerShell 7), для дашборда невидим — статус «остановлен», кнопки не остановят. При этом в `docs/log.md` (13:40) заявлено «старый слушатель ищется независимо от имени процесса (powershell.exe/pwsh.exe)» — расхождение документа с кодом.
5. **Смесь языков в журнале**: итоги по-русски (`ОТПРАВЛЕНО`, `ПРИНЯТО`), диагностика по-английски (`FATAL: receiver did not pick up...`, FileTransfer.ps1:361). Фильтровать и читать труднее, чеклисты LogTracker (`-Stats`, :169–179) ищут английские паттерны.
6. **Документация отстаёт от кода**: в README нет раздела про веб-дашборд (появился 2026-10-08, README не обновлялся); SPEC 8.3 не знает про префиксы `ОТПРАВКА/ОТПРАВЛЕНО/ПРИНЯТО/ПРИЁМ/НЕ ПЕРЕДАНО/WEB/DROP`; SPEC 8.4 и таблица 5.1 держат старый дефолт ротации 500 строк, тогда как в setcp.ini уже `MaxLogLines=10000`.

## 5. Замечания по коду

**Корректность**
- FileTransfer.ps1:2134 — `WARNING` попадает в класс `bad` (красный) вместе с `FAIL|FATAL|ERROR`; предупреждение и ошибка неотличимы. Разделить на два класса.
- FileTransfer.ps1:1986 — фильтр истории дашборда дублирует набор паттернов из status-writer (:1518) с расхождением: в первый добавлены `CLEAR-DISK|DEL-MARKER|AUTOUPDATE`, во второй нет. Один источник списка — меньше рассинхрона.

**Обработка ошибок**
- dashboard.html:66–67 — `xhr.onload` не проверяет `xhr.status`: ответ 404/500 считается успехом, счётчик уменьшается, страница перезагружается; пользователь видит «ничего не произошло».

**Читаемость**
- dashboard.html:57 — `dz.innerHTML = 'Передача...'` затирает содержимое зоны вместе с подсказкой; после серии загрузок подписка `dragover` остаётся, но текст не вернуть. Мелочь, но вклад в «сделано кое-как».

**Производительность**
- FileTransfer.ps1:1985–1987 — на каждый запрос (в т.ч. каждую автоперезагрузку через 3 сек) читается весь журнал до 10000 строк + регулярка. Приемлемо, но при росте журнала — читать хвост (например, последние 200 КБ).

## 6. Интерфейс

- **Цвета** (dashboard.html:7, 21): зелёный используется и для индикаторов («слушатель работает», «на связи»), и для событий отправки — пользователь читает поток как «всё ОК», хотя в потоке есть и ошибки. Запрос пользователя корректен: события передачи — **серый служебный**, жёлтый — предупреждения, красный — ошибки, зелёный — только индикаторы статуса.
- **Обратная связь передачи**: в истории дашборда нет строк старта (`ОТПРАВКА`/`ПРИЁМ` не проходят фильтр :1986) — передача выглядит «оборванной»; цельная запись «от начала до конца» собирается в голове.
- **Автообновление**: полная перезагрузка страницы каждые 3 сек — мигание, потеря позиции прокрутки, обрыв drop-загрузки.
- **Drop-зона без прогресса и без ошибок**: «осталось N» при любом исходе; обрыв или 500 пользователь не видит.
- **Тулбар**: опасное («Рестарт слушателя») и безобидное («SyncDir») сгруппированы без визуального различия; подтверждение (confirm) есть — хорошо.

## 7. Аналитика и данные

Профиль журнала (по живому `C:\CHANGE\FileTransfer.log`): строки `[ts] [Метка] Сообщение`, метки `Watch/Pack/PackAuto/Web/...`; пропусками и дублями по ключу не страдает; ротация 10000 строк (неделя истории).

- Формат итоговой строки информативен (имя, МБ, секунд), но **число чанков и ретраев** в итог не попадает — не видно, сколько раз передача откатывалась.
- Строки `===== START/END =====` позволяют считать сеансы, но Web-процесс их не фильтрует в историю — правильно.
- Время доставки считаемо только попарно `ОТПРАВКА → ОТПРАВЛЕНО` по имени файла: на дашборде пары разнесены по разным контурам (локальный журнал + status-*.json) — совпадение имён от обеих сторон может задваивать строки.

1. **Цветовая схема журнала**: события передачи/статусов — серый; WARNING — жёлтый; FAIL/FATAL/ERROR/НЕ ПЕРЕДАНО — красный; зелёный — только индикаторы «работает/на связи» (dashboard.html:21 + классификация FileTransfer.ps1:2131–2134).

## 9.1. Анализ: сеть вместо буфера обмена (выполнено после аудита)

**Текущий транспорт.** Буфер обмена RDP — текстовый канал: Base64 (+33% накладных
расходов), чанки 5 МБ, ACK-цикл «положили → приёмник очистил буфер → опрос 400 мс».
Оценка потолка: **~2–4 МБ/с полезной скорости** на типовом RDP-канале. Каждая передача
монополизирует буфер ОБЕИХ сторон: заблокированы пользовательские Ctrl+C/Ctrl+V,
встречные status-файлы ждут.

**Что чинит сеть:**

| Ограничение буфера | Как снимает сетевой транспорт |
|---|---|
| Нет обратной доставки ошибки сборки (инцидент `materials2.zip`: «ОТПРАВЛЕНО» у отправителя, FAIL на приёмнике) | Финальный ответ транспорта = результат сборки |
| ACK-цикл на каждый чанк (пауза, опрос 400 мс) | Подтверждение HTTP-ответом POST без опроса |
| Конфликт с пользовательским буфером (Ctrl+C/Ctrl+V) | Буфер не задействован вовсе |

**Вариант A (рекомендуемый): TCP-транспорт поверх HttpListener** (уже есть в проекте —
Web на 8123). Слушатель на порту 8124 на внутреннем контуре, отправка чанков HTTP
POST-ами, тот же JSON-протокол, тот же контроль MD5, финальный ответ = результат
сборки (устраняет ложное «ОТПРАВЛЕНО»). Буфер обмена остаётся фолбэком при
недоступности сети.

**Вариант B: SMB-шара как транспорт** (сеть уже есть, RDP не нужен). Минус:
требования политики к шарам между контурами.

**Ограничения/риски.** RDP-сценарий существует именно потому, что прямой сетевой
доступ между контурами может быть ЗАПРЕЩЁН политикой (порты/фаервол) — сеть не
заменяет буфер, а дополняет там, где порт открыт. Нужен ключ в `setcp.ini`
(`Transport=clipboard|network|auto`) и правило фаервола на приёмнике.

**Трудоёмкость: M** — протокол чанков переиспользуется, новый транспорт — тонкий
адаптер вокруг `Send-FileInChunks`/приёмника.

## 10. Что не проверено

- `Install.ps1`, `CreateShortcuts.ps1`, `Hotkeys.ahk` — в этой сессии не читались (в прежнем аудите от 2026-10-07 — прочитаны).
- Веб-дашборд не открывался в браузере и не воспроизводился живой обрыв drop-загрузки — вывод о причине сделан по коду (meta refresh + отсутствие проверки `xhr.status`) и по жалобе пользователя.

- Лог под `pwsh.exe`-слушателем не воспроизводился.
- Реальные параллельные передачи с двух контуров не моделировались (сорт по строке времени T при расхождении часов).
