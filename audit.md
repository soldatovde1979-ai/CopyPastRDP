# audit.md — аудит проекта CopyPast

Дата: 2026-10-07 · Аудит только для чтения, правки не вносились.

---

## 1. Паспорт

**Что это:** CopyPast — утилита передачи файлов между двумя ПК через RDP-буфер обмена
(файл → Base64 → JSON-пакет → буфер → приёмник). Вторая функция — фоновая синхронизация
папки `C:\CHANGE\disk` между двумя «контурами» (локальный ПК ↔ удалённая машина по RDP).

**Для кого:** один пользователь-администратор (разработчик = пользователь); развёртывание
на двух машинах, файлы передаются через защищённый RDP-канал.

**Стек:** Windows PowerShell 5.1 (4 скрипта), AutoHotkey v2 (хоткеи), INI-конфиг. Сборки и
зависимостей нет — только встроенные средства Windows.

**Точки входа:**

| Файл | Роль | Проверка |
|---|---|---|
| `FileTransfer.ps1` (~1470 строк) | Ядро: Pack / Unpack / Watch / синхронизация / самообновление | прочитан, парсер PS — OK, `LocalShow` запущен (exit 0) |
| `setcp.ini` + `setcp.local.ini` | Конфигурация общая/локальная | прочитан, запущен через `LocalShow` |
| `Install.ps1` | Установка в `C:\CHANGE`, перезапуск слушателя, рассылка обновлений в SyncDir | прочитан |
| `CreateShortcuts.ps1` | Ярлыки SendTo + автозапуск «СЛУШАТЕЛЬ» | прочитан |
| `LogTracker.ps1` | Просмотр/статистика журнала | прочитан |
| `Hotkeys.ahk` | Хоткеи AHK: передача, раскладка | прочитан, не запускался |
| `README.md`, `SPEC.md`, `docs/log.md` | Документация | прочитаны |
| `FileTransfer.log`, `disk\change.log` | Журналы (на живом контуре `C:\CHANGE`) | tail просмотрен |

`data/` в проекте нет; роль данных играют журналы (текстовые, парсятся регулярками).

## 2. Плюсы решения

- **Документация уровня спецификации протокола:** `SPEC.md` описывает форматы пакетов,
  тайминги, формат журнала; README содержит сценарии диагностики («файлы лежат в disk,
  но не уходят»). Для solo-проекта это редкость и хорошая страховка от «знания в одной голове».
- **Персистентная защита от петель синхронизации:** `change.log` с типами
  SENT/RECEIVED/SNAPSHOT переживает перезапуск слушателя
  (`FileTransfer.ps1:Initialize-ChangeLog`); принятый файл не уходит обратно.
- **Конфигурация вынесена из кода**, включая грамотное разделение общий/локальный INI
  (`setcp.local.ini` не синхронизируется) — решение под реальную асимметрию контуров.
- **Механизм «свой-чужой» по `Origin`** (`FileTransfer.ps1:Watch-Clipboard`) — два
  слушателя на одном RDP-канале не съедают пакеты друг друга.
- **Backoff ретраев** (введён 2026-10-07): после таймаута ACK повтор откладывается
  на растущий интервал — буфер больше не забивается повторами при выключенном слушателе
  на другом контуре (`FileTransfer.ps1:Register-SyncFailure`).
- **Тихие места озвучены в конфиге:** комментарии INI предупреждают про
  `AutoUpdate=1` («любой файл с таким именем считается обновлением») и двойной слушатель.

## 3. Минусы и слабые места

- **Дублирование чанковой логики:** один и тот же протокол «положи чанк → жди ACK»
  реализован дважды — `FileTransfer.ps1:Pack-Files` (ручная отправка) и
  `FileTransfer.ps1:Send-SyncFile` (синхронизация). Правка протокола требует синхронных
  правок в двух местах — сегодня это уже источник расхождений (только в `Send-SyncFile`
  есть RelPath и восстановление буфера).
- **Три реализации парсера INI:** `FileTransfer.ps1:Get-IniContent` (с секциями),
  `Install.ps1:Get-IniKey` и `LogTracker.ps1:Get-IniValue` (обе без секций) — поведут
  себя по-разному на одинаковом файле.
- **Монолит на ~1470 строк** — осознанный выбор (развёртывание одним файлом + автоперенос
  через SyncDir), но сопровождение уже тяжёлое: правка затрагивает 5–6 функций сразу.
- **Текстовый журнал с ротацией в 500 строк** (`FileTransfer.ps1:Rotate-Log`): при
  heartbeat раз в 60 сек история живёт ~1 час — диагностика «что было вчера» невозможна.
- **Повреждённая запись в `docs/log.md`** (блок 2026-09-04 23:10): текст обрезан и
  склеен («…а синхроение в журнале…» / строка, начинающаяся с «низация сама доставит…») —
  журнал разработки в этом месте нечитаем.

## 4. Риски

| Риск | Где | Критичность | Вероятность | Что делать |
|---|---|---|---|---|
| **Самообновление без проверки целостности**: любой файл с именем `FileTransfer.ps1`/`setcp.ini` в корне SyncDir применяется и слушатель перезапускается. Повреждённый файл (обрыв передачи, чей-то случайный файл) убивает слушателя на **обоих** контурах, восстановление — вручную | `FileTransfer.ps1:Unpack-Files` (блок AUTOUPDATE, `AutoUpdate`) | высокая | низкая | перед перезапуском парсить новый скрипт (`Parser::ParseFile`) и откатывать при ошибке |
| **Порча чанкового файла при сбое ACK**: нет контрольных сумм; если отправитель не получил ACK и повторяет чанк, а приёмник уже его дописал, чанк допишется дважды | `FileTransfer.ps1:Send-SyncFile` + `Unpack-Files` (append в `.part`) | средняя | низкая | контрольная сумма в последнем чанке или проверка длины `.part` перед append |

| **Потеря диагностики**: журнал 500 строк при heartbeat 60 сек → история на ~1 час; сбой ночью не диагностировать | `FileTransfer.ps1:Rotate-Log`, `setcp.ini:MaxLogLines` | средняя | высокая | увеличить `MaxLogLines` до 5000 или ротация по дате (`FileTransfer.2026-10-07.log`) |
| **Хардкод `C:\CHANGE` в ярлыках**: `CreateShortcuts.ps1` игнорирует `-Destination` из Install — при смене пути ярлыки молча сломаются | `CreateShortcuts.ps1:28` | средняя | низкая | путь брать из реального расположения `FileTransfer.ps1` |

| Ссылка на корп. ресурс зашита в коде хоткеев (не секрет, но меняется правкой файла) | `Hotkeys.ahk:96` | низкая | — | вынести в текстовый файл рядом |

## 5. Замечания по коду

**Корректность**
- `Install.ps1:Get-IniKey` ищет ключ по всему файлу без секций и берёт первое совпадение —
  на файле с двумя `LogFile=` (или ключом в комментарии) вернёт не то. Исправление:
  читать секцию `[Paths]` (парсер из `FileTransfer.ps1` уже умеет).
- `LogTracker.ps1:Show-Stats` суммирует все `\(([\d.]+) MB\)` — «Packing … (1.85 MB)» и
  «OK: Sent … (1.85 MB)» — один и тот же файл учтён дважды. Исправление: считать только
  один тип строк (например, `Sent .* files to clipboard`).
- `Hotkeys.ahk:SwitchLayout` возвращает string при `dir="none"` и объект иначе — вызов
  `result.text` на string дал бы пустоту; в `^!sc013` спасает проверка `IsObject`,
  в `Pause::` — тоже. Единообразный `return`-объект убрал бы хрупкость.
- `FileTransfer.ps1:Unpack-Files`: `GetClipboard`-фолбэк при исключении
  (`$clipData = Get-Clipboard -Raw`) выполнится, если `Add-Type` упал, но следующая
  строка `Get-Clipboard` без `-Raw` вернёт строки поsplit'ованно — мелочь, но при
  бинарных данных чревато. Исправление: один путь чтения с try/catch.

**Обработка ошибок**
- `LogTracker.ps1:35` `$ErrorActionPreference = "SilentlyContinue"` на весь скрипт —
  реальные сбои (нет доступа к файлу) выглядят как «ничего не найдено». Исправление:
  `Continue` только вокруг `Get-Content`.
- `FileTransfer.ps1:Write-Log` глушит ошибку записи журнала (`catch {}`) — приемлемо,
  но при переполнении диска слушатель работает «молча»: heartbeat-проверка не спасает.
  Некритично, зафиксировано как факт.

**Читаемость**
- `FileTransfer.ps1:Pack-Files` + `Send-SyncFile` — вынести общий код чанков в
  `Send-Chunked($fileInfo, $relPath)` (одна функция, параметр — payload).
- `FileTransfer.ps1:Restart-Listener` вызывает `exit 0` внутри функции — управление
  потоком через выход из процесса; лучше возвращать флаг и `exit` в диспетчере.

**Производительность**
- `FileTransfer.ps1:Scan-SyncDir` рекурсивно обходит SyncDir каждую секунду — при
  тысячах файлов станет заметным. Исправление: `.FileSystemWatcher` или увеличение
  `SyncPollMs`. Пока файлов десятки — не трогать.

## 6. Интерфейс

- **Обратная связь о передаче — только в журнале.** Пользователь после «SEND FILE» не
  видит, ушла ли посылка: окно закрывается, звук — единственный сигнал. Короткий вывод
  в консоль ярлыка (SendTo) уже есть — но окно `WindowStyle=7` свёрнуто. Показывать
  всплывающий toast/MsgBox с итогом при ошибке (и молчать при успехе) — дёшево.
- **`Hotkeys.ahk` MsgBox при каждом старте** — окно-подсказка закрывается по таймауту T5,
  но при автозагрузке раздражает. Спрятать за `- silent`-параметром.
- **RECEIVE FILE — двухфазное поведение:** файл сначала падает в `IN` (слушателем), потом
  переносится в выбранную папку (UnpackTo). Если окно `ManualReceiveWindowSec` (300 сек)
  истекло, пользователь получит «нет свежих файлов», хотя файл только что «принял». Это
  задокументировано, но неочевидно из UI. Возможное улучшение: брать последний
  «незабранный» файл по манифесту, а не по времени.
- **LogTracker** — понятное меню, подсветка уровней, статистика: сделано хорошо.

## 7. Аналитика и данные

`data/` нет — раздел заполняется по журналам (`FileTransfer.log`, `change.log`).

**Качество данных:** журнал — текст `[дата] [метка] сообщение`; парсится регулярками
(`LogTracker.ps1:Show-Stats`), объёмы — только из свободного текста `\(([\d.]+) MB\)`.
Ротация 500 строк делает накопительную статистику невозможной в принципе. `change.log`
структурирован лучше (`дата|ТИП|путь|размер|ticks`), но пересоздаётся при >2000 строк —
история синхронизации обнуляется.

**Что может ввести в заблуждение:** `-Stats` показывает «Передано данных» с двойным
счётом (см. §5) и без деления «отправлено/принято» — цифра скорее всего завышена вдвое.

## 8. Какие отчёты и графики добавить

*Папки `data/` нет; «данные» — журналы. Блок 1 — что можно построить из текущих полей
(дата-время, метка режима, текст сообщения, MB в тексте).*

**Можно построить из текущих полей:**

| Вопрос пользователя | Отчёт | Тип | Поля | Трудоёмкость |
|---|---|---|---|---|
| Сколько и чего передано за день? | Передано файлов и МБ по дням/режимам | столбцы | timestamp, метка, `(N.NN MB)` | S |
| Как часто и почему падает передача? | Ошибки/предупреждения по типам (FAIL/FATAL/ACK timeout) | таблица + тренд | timestamp, текст | S |
| Как долго идёт файл до ACK? | Гистограмма «SetText → cleared» по чанкам | линия | timestamp соседних строк | M |
| Что синхронизируется между контурами? | Топ файлов/папок по числу SENT в `change.log` | столбцы | путь, ТИП, размер | S |
| Жив ли слушатель? | Аптайм по heartbeat-строкам (пропуски = падение) | линия | timestamp `Watch alive` | S |

**Не хватает данных:** устойчивая статистика невозможна, пока журнал ротируется до
500 строк. Нужно: писать параллельный машиночитаемый лог (CSV: timestamp, mode, event,
file, bytes, status) без ротации — тогда все отчёты выше станут надёжными и появятся
динамика за месяцы и «перечень проблемных файлов».

## 9. Что сделать в первую очередь

**Quick wins:**
1. Ротация журнала по дате или `MaxLogLines=10000` (`setcp.ini`) — диагностика перестанет
   теряться через час.
2. Проверка синтаксиса принятого `FileTransfer.ps1` перед AutoUpdate-перезапуском
   (3 строки: `Parser::ParseFile`, при ошибке — не применять).
3. Починить повреждённую запись в `docs/log.md` (блок 2026-09-04 23:10).
4. `LogTracker.ps1`: заменить `SilentlyContinue`, исправить двойной счёт MB в `-Stats`.
5. `Install.ps1:Get-IniKey` — читать ключ в секции, а не по всему файлу.

**Крупное:**
6. Вынести общую чанковую отправку в одну функцию (Pack/Send-SyncFile).
7. Контрольная сумма чанков (CRC в пакете, проверка приёма) — устраняет тихую порчу файлов.

## 10. Что не проверено

- Реальная сквозная передача Pack → Watch через RDP-буфер (двухконтурный сценарий) —
  не запускалась; проверена только загрузка конфига (`LocalShow`) и синтаксис.
- `Hotkeys.ahk` не запускался (нет среды AHK в сессии) — анализ по чтению.
- Поведение при папке SyncDir с тысячами файлов (производительность скана) — оценка
  умозрительная.
- `ReadMe.docx` не читался (дублирует README по описанию; в аудит не включён).
- Поведение слушателя при переполнении буфера очень большим чанком (>~100 МБ Base64)
  не проверялось — SPEC это оговаривает как ограничение RDP, но порог деградации неизвестен.
- Просмотрен tail живого журнала, а не весь файл; статистика сбоев за месяц недоступна
  из-за ротации (см. §4).
